# V1.0 Migration Plan

## 0. 文档目的与边界

本计划将当前本地 Room 数据库 **v20** 和 Kotlin 实现，分阶段迁移至已冻结的 V1.0 单店卫浴门店管理系统。

本阶段只建立迁移基线和实施计划，**不修改 Kotlin、Gradle、Room schema 或数据库文件**。

V1.0 范围：客户、订单、订单项/工单、产品、供应商、库存、回款、跟进、员工多角色权限、操作日志、备份恢复与经营看板。\
不在 V1.0 范围：报价、采购单、完整财务账本、审批、云同步、云盘、多门店。

## 1. 当前数据库 v20 基线

当前 `AppDatabase` 版本为 **20**，包含 13 个 Entity：

| 当前表 | 当前用途 | V1.0 处置 |
|---|---|---|
| `stores` | 门店主档 | 保留并补审计/同步兼容字段 |
| `staff` | 员工账号与单一角色 | 保留；单一 `role` 废弃为权限来源 |
| `customers` | 客户主档 | 保留并增加负责人、生命周期、软删除字段 |
| `suppliers` | 供应商 | 保留并补审计、软删除字段 |
| `products` | 产品目录 | 保留；金额改为分单位 Long |
| `orders` | 销售订单 | 保留；状态拆分、金额改 Long、责任人规范化 |
| `order_items` | 订单产品/工单 | 保留；采购/安装状态拆分、金额改 Long |
| `payments` | 客户回款 | 保留；改为不可删除的审计记录 |
| `follow_ups` | 跟进/基础回访 | 保留并增加责任、审计、软删除字段 |
| `ledger_entries` | 简易账本 | 降级为遗留只读表；V1.0 不新增、不使用 |
| `action_logs` | 操作日志预留 | 保留并扩展为真正审计日志 |
| `order_item_status_logs` | 工单状态历史 | 保留为不可变履约日志 |
| `inventory_items` | 当前库存余额 | 保留并简化；增加独立库存流水 |

V1.0 新增表：

```text

permissions
role_permissions
staff_roles
order_staff_assignments
inventory_transactions
app_config
```

## 2. v20 → V1.0 详细迁移表

### 2.1 保留并扩展的表

| 表 | v20 主要问题 | V1.0 调整 |
|---|---|---|
| `stores` | 无同步标识、软删除、完整审计 | 增加 `remoteId`、状态、创建/更新人、版本、软删除字段；店铺只关闭，不物理删除 |
| `staff` | 单一 `role`；密码哈希实际为明文；缺审计/软删除 | 保留账号资料；增加 PBKDF2 密码元数据、审计、软删除、版本；`role` 迁移后废弃 |
| `customers` | 无负责人、生命周期、软删除 | 增加 `ownerStaffId`、来源、阶段、最近/下次跟进、审计、软删除、版本、`remoteId` |
| `suppliers` | 只有创建时间；无停用与软删除 | 增加编号、启用状态、更新时间、审计、软删除、版本、`remoteId` |
| `products` | `Double` 金额；仅关联供应商；无软删除 | 金额改 `Long` 分单位；增加产品编号、品牌、单位、成本、停售/软删除、审计、版本、`remoteId` |
| `orders` | 单一状态；金额 Double；负责人列表序列化；可级联删除 | 增加销售负责人、业务/支付状态、金额 Long、已收/未收快照、取消信息、审计、版本、软删除；责任人迁至关联表 |
| `order_items` | 单一履约状态；金额 Double；无完整审计 | 金额 Long；拆 `purchaseStatus` 与 `installationStatus`；增加行号、审计、版本、`remoteId` |
| `payments` | 无单号、确认/作废/退款状态；金额 Double | 金额 Long；增加类型、方向、状态、确认/作废审计、单号、交易号、版本、`remoteId`；禁止删除 |
| `follow_ups` | 跟进责任不清、审计不足 | 增加 `storeId`、负责人、类型、完成时间、审计、软删除、版本、`remoteId` |
| `action_logs` | 无店铺、前后变更摘要；员工删日志级联 | 增加 `storeId`、操作者、来源、摘要、前/后数据、请求标识；仅新增、永不删除 |
| `order_item_status_logs` | 仅记录目标状态；无门店与备注 | 增加 `storeId`、`fromStatus`、`toStatus`、操作者、备注、来源、`remoteId`；仅新增、永不删除 |
| `inventory_items` | 直接改余额；预占设计超出 V1；无版本 | 简化为 `availableQuantity` 当前余额；移除预占字段；增加审计、版本、`remoteId` |

### 2.2 遗留表

| 表 | V1.0 处理 |
|---|---|
| `ledger_entries` | 不删除表或历史数据；停止新增写入、从 V1.0 页面和看板移除。V2 重做财务模型前保持只读归档。 |

### 2.3 新增表

| 新表 | 用途 | V1.0 必要性 |
|---|---|---|
| `roles` | 系统预置角色 | 支持多岗位 |
| `permissions` | 资源、操作、数据范围定义 | 权限与角色分离 |
| `role_permissions` | 全局角色—权限映射 | 系统角色共享 |
| `staff_roles` | 员工—角色多对多及范围值 | 一个员工多个岗位 |
| `order_staff_assignments` | 订单协作职责 | 销售、设计、采购、仓库、安装、财务责任追踪 |
| `inventory_transactions` | 不可变库存流水 | 可追溯入库、安装出库、调整、退货 |
| `app_config` | 本地运行与备份恢复配置 | 当前门店/员工、最近备份/恢复信息 |

## 4. Room Migration 顺序

不建议一个不可回归的大 Migration 同时改变权限、金额、库存和业务逻辑。采用连续、可测试的手写 Migration。

### 阶段 0：迁移基线（不改 schema）

1. 固定 v20 schema 和真实/模拟 v20 数据样本。
2. 为 v20 创建 Migration 测试数据库。
3. 记录每张表行数、订单金额总计、回款总计、库存总计。
4. 禁止再以 `fallbackToDestructiveMigration()` 作为生产迁移方案。

### 阶段 1：权限 Schema Migration

1. 新建 `roles`、`permissions`、`role_permissions`、`staff_roles`。
2. 写入系统角色和权限映射。
3. 按旧 `Staff.role` 迁移员工角色：
   - `BOSS` → `BOSS`，并补 `SALES`、`FINANCE`；
   - `STAFF` → 初始 `SALES`；
   - `SHAREHOLDER` → 初始 `FINANCE`，需首次登录确认。
4. 保留旧 `staff.role`，但停止作为鉴权来源。

### 阶段 2：审计、责任与状态 Schema Migration

1. 新建 `order_staff_assignments`、`app_config`。
2. 为核心表添加 `remoteId`、审计字段、版本、软删除字段。
3. 为 `Customer` 添加 `ownerStaffId`；历史客户先回填为订单创建人或门店老板。
4. 为 `Order` 添加 `salesStaffId`、`businessStatus`、`paymentStatus`。
5. 将 `responsibleStaffIds` 解析写入 `order_staff_assignments`。
6. 为 `OrderItem` 新增 `purchaseStatus`、`installationStatus`，由旧状态映射初始化。

旧订单项状态映射：

| 旧状态 | 新采购状态 | 新安装状态 |
|---|---|---|
| `NOT_ORDERED` | `PURCHASE_PENDING` | `WAIT_INSTALL` |
| `ORDERED` | `PURCHASED` | `WAIT_INSTALL` |
| `IN_TRANSIT` | `PURCHASED` | `WAIT_INSTALL` |
| `IN_STOCK` | `ARRIVED` | `WAIT_INSTALL` |
| `INSTALLING` | `ARRIVED` | `INSTALLING` |
| `INSTALLED` | `ARRIVED` | `DONE` |

### 阶段 3：金额 Migration

1. 将所有 `Double` 金额转换为 `Long` 分单位。
2. 换算规则：`round(oldDouble × 100)`。
3. 从订单项重新计算订单总额、最终金额。
4. 从有效回款重新计算已收和未收金额。
5. 验证迁移前后金额差仅在历史浮点误差允许范围内。
6. 旧 Double 列在过渡版本保留只读；验证完成后在下一版本移除。

### 阶段 4：库存与回款审计 Migration

1. 新建 `inventory_transactions`。
2. 将现有 `inventory_items.quantity` 初始化为 `availableQuantity`。
3. 为每条当前库存创建一条 `OPENING_BALANCE` 初始化流水。
4. 移除/废弃库存预占字段。
5. 为 `payments` 增加类型、方向、状态、确认、作废和退款字段。
6. 历史回款全部初始化为 `ACTIVE + CONFIRMED`，确认人使用原 `staffId`。

### 阶段 5：安全、备份与旧字段清理

1. 迁移密码数据：首次旧密码登录成功后重新使用 PBKDF2 派生保存；或在受控数据重置时强制改密。
2. 新建/填充 `AppConfig`。
3. 实现备份恢复后，再删除不再使用的 DataStore 会话角色字段。
4. 所有业务代码完成切换和 Migration 测试后，移除旧 `Staff.role`、`Order.status`、`Order.responsibleStaffIds`、旧金额 Double 字段。
5. `ledger_entries` 维持遗留只读，不在 V1.0 业务写入路径中使用。

## 7. 业务层新增 Service / UseCase

建议新增明确的业务服务，而不是继续把跨表规则堆在 ViewModel 或 `DatabaseModule`。

| Service / UseCase | 职责 |
|---|---|
| `PermissionManager` | 登录时加载角色、权限、范围到内存；提供统一鉴权 API |
| `AccessControlService` | 解释 OWN/STORE 范围，判断员工能否访问指定客户、订单、工单、回款 |
| `RoleAssignmentService` | 分配/移除角色；校验分配人权限范围；保证至少一名有效老板 |
| `OrderService` | 创建、编辑、取消订单；订单项同步；金额重算；订单责任人分配 |
| `OrderAmountCalculator` | 订单项、优惠、已收、未收的 Long 分单位统一计算 |
| `WorkOrderService` | 订单项采购/安装状态迁移；状态合法性；更新履约状态日志 |
| `InventoryService` | 入库、安装出库、调整、退货；余额和库存流水同事务更新 |
| `PaymentService` | 登记、确认、作废、退款；重算订单已收/未收；写审计日志 |
| `AuditLogService` | 统一写入 ActionLog，避免业务模块自行拼接日志规则 |
| `BackupManager` | 备份、元信息校验、恢复前自动备份、恢复后会话清理 |
| `DemoDataInitializer` | 仅 Debug/内部测试；生成可测试的账号、权限、客户、订单、库存与回款 |

## 8. 冻结要求核对

| 冻结要求 | 结论 | 实施要求 |
|---|---|---|
| PermissionManager 权限缓存 | 已纳入 | 登录加载有效角色/权限/范围；业务层禁止直查 RolePermission 做鉴权 |
| Order 状态拆分 | 已纳入 | `Order.businessStatus`、`Order.paymentStatus`；`OrderItem.purchaseStatus`、`installationStatus` |
| 密码哈希升级 | 已纳入 | PBKDF2WithHmacSHA256；Salt、迭代次数、算法版本、恒定时间比较 |
| 软删除策略 | 已纳入 | 主数据软删除；业务单据用取消/作废；不可变流水永不删除 |
| Payment 不可删除 | 已纳入 | 仅 `ACTIVE`、`VOID`、`REFUND`；作废/退款留痕 |
| InventoryTransaction 不可删除 | 已纳入 | 仅新增；错误以反向流水修正 |
| Ledger 降级 | 已纳入 | `ledger_entries` 只读遗留；移除 V1 页面和新写入，不参与 V1 看板 |
