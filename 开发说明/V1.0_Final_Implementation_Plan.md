# V1.0 最终实施计划

> 状态：冻结基准。本文是后续开发、Migration、测试和验收的唯一基准；旧规划如有冲突，以本文为准。
>
> 本文不授权修改生产代码、Entity、DAO、Repository、ViewModel、UI 或执行正式 Migration。

## 1. 产品边界

### 1.1 定位

V1.0 是一套单店、本地 Android、10 人以内、多岗位协作的门店管理系统。技术采用 Compose、MVVM、Hilt、Repository、Room；离线优先，不做云同步和多门店。

业务闭环：客户 → 订单 → 订单项/工单 → 到货入库 → 安装出库 → 回款/账本 → 跟进。

### 1.2 必须交付

- 登录；首页经营看板。
- 客户、客户跟进；订单、订单项、工单。
- 产品、供应商；库存与库存流水。
- 回款；基础日常收支账本。
- 员工管理、多角色分配、操作日志。
- 数据备份、恢复与基础设置。

老板看板至少显示：销售额、回款额、待收金额、账本收入、账本支出、净收支、待下单/待到货/待安装数量与库存概览。

### 1.3 明确不做

- 云同步、服务端、WebSocket、多门店。
- 自定义角色或自定义权限页面。
- 报价单、采购单、供应商应付账款体系。
- 库存预占、锁库存、批次、库位、复杂调拨。
- 售后工单、审批流、云盘、附件管理。
- 复式记账、总账、会计凭证、税务、复杂成本结转、银行自动对账和复杂利润核算。

## 2. 角色、权限与数据范围

### 2.1 系统角色

| 角色 | 职责 |
|---|---|
| `BOSS` | 全店管理、员工角色、备份恢复、经营数据 |
| `SALES` | 客户、本人订单、跟进、回款登记 |
| `DESIGNER` | 客户需求、产品选择、本人订单协作 |
| `PURCHASER` | 供应商、产品、下单与物流状态 |
| `WAREHOUSE` | 到货入库、库存调整、库存查看 |
| `INSTALLER` | 本人安装任务、安装状态、安装备注 |
| `FINANCE` | 回款确认、作废、退款、账本与经营数据 |

员工可同时拥有多个系统角色。系统角色与权限映射全局共享，不带 `storeId`。

### 2.2 最终权限模型

`Staff → StaffRole → Role → RolePermission → Permission`。

有效权限是全部有效角色权限的并集。`Staff` 不保存权限字段，也不以单一角色为权限来源。Permission 必须包含 `resource`、`action`、`dataScope`；范围编码为 `OWN`、`STORE`、`DEPARTMENT`、`ALL`，V1 只实现 OWN 和 STORE，后两项仅预留。

### 2.3 PermissionManager 缓存

登录后 PermissionManager 一次性加载以下会话缓存：

- `staffId`、`storeId`；
- `roleCodes`；
- `effectivePermissions`；
- `permissionScopes`。

UI、ViewModel、Repository 统一经 PermissionManager 进行权限判断；业务层禁止为鉴权反复直接查询 RolePermission。UI 只负责入口显示，所有写操作必须在业务层再次校验。老板也必须经过同一系统，禁止大量使用 `if (role == BOSS)`。

缓存必须在登录、登出、员工禁用、角色变更和数据库恢复后刷新或清空。

### 2.4 OWN / STORE 规则

客户本人：`Customer.ownerStaffId == currentStaffId`。

订单本人满足其一：`Order.salesStaffId == currentStaffId`；或存在有效 `OrderStaffAssignment`，且 `assignmentRole` 为 SALES 或 DESIGNER。

PURCHASER、WAREHOUSE、INSTALLER、FINANCE 不得仅因参与订单而取得订单价格、产品或客户编辑权。V1 默认 SALES 可查看全店客户但仅编辑本人客户；BOSS 可全店编辑；没有 `CUSTOMER_EDIT_ALL` 的员工不得编辑他人客户。

### 2.5 角色授权边界

仅拥有 `STAFF_MANAGE` 且满足边界的员工可分配角色：只能管理本店有效员工；待分配角色的全部权限必须是分配人有效权限的子集；BOSS 只能由 BOSS 授予或移除；不得移除最后一名有效 BOSS；角色变动必须事务化并写 ActionLog。

`StaffRole.scopeValue` 可空，预留未来部门范围；不放入全局 Permission，以免系统权限被绑定到某门店部门。

## 3. 数据库通用约定

- 所有主业务 Entity 使用本地 `id: Long` 自增主键。
- 需要未来同步兼容的业务 Entity 创建时生成 `remoteId: String UUID`，V1 不执行云同步。
- 所有业务金额是 `Long`，单位为人民币分；新业务禁止 Double 金额计算。
- `version: Long` 预留未来乐观锁；V1 本地单设备不实现并发冲突处理。
- 主数据采用软删除；订单采用取消；回款/账本采用作废或退款；日志/流水不可变。
- 新增非空字段 Migration 时必须给默认值或先允许空再回填。

## 4. 最终 Entity 清单（20 个）

| `OrderStaffAssignment` | 订单职责：storeId、orderId、staffId、assignmentRole、主责、分派人/时间、removedAt；`id + remoteId` | Store、Order、Staff、分派人；orderId+staffId+assignmentRole 唯一 | 不需 version；不物理删除，removedAt 失效；SALES/DESIGNER 可参与 OWN 判断 |

| Entity | 作用、关键字段 | 外键与索引 | 审计、删除与关系 |
|---|---|---|---|
| `OrderItemStatusLog` | 不可变工单轨迹：storeId、orderItemId、from/to 状态、操作人、时间、备注、来源；`id + remoteId` | Store/OrderItem RESTRICT，operator SET_NULL；订单项+时间、门店+时间索引 | 只插入，不修改、不删除；记录采购/安装状态历史 |

| `InventoryTransaction` | 不可变库存流水：门店、库存、产品、订单/项、类型、变更前后数量、操作人、时间、备注；`id + remoteId` | inventory SET_NULL，product RESTRICT，order/item/operator SET_NULL；门店+时间、产品+时间、订单项索引 | 只插入，不修改、不删除；余额更新与流水同一事务 |

| `LedgerEntry` | 基础账本：门店、单号、收入/支出、分类、金额、日期、关联订单/客户/回款、经办人、状态；`id + remoteId` | Store RESTRICT，其余关联 SET_NULL；门店+单号唯一、日期、方向+分类、回款、订单索引 | 审计、version；不可删除，仅 ACTIVE/VOID；回款收入为 PAYMENT_INCOME，其他收入/采购/经营/其他支出直接登记 |
| `FollowUp` | 跟进：门店、客户、订单、类型、状态、负责人、计划/完成时间、内容、结果、下次跟进；`id + remoteId` | Store/Customer RESTRICT，Order/员工 SET_NULL；负责人+状态+计划时间、客户、订单索引 | 审计、version、软删除；不物理删除 |
| `ActionLog` | 安全与业务审计：门店、操作人、类型、目标、摘要、前后数据、来源、请求标识、时间；`id + remoteId` | operator→Staff SET_NULL；业务目标不设强外键；门店+时间、操作人+时间、目标索引 | 只插入，不修改、不删除；员工禁用/软删除后仍保留 |

### 4.4 关键金额字段

`Order`：`totalAmountFen`、`discountAmountFen`、`finalAmountFen`、`downPaymentFen`、`receivedAmountFen`、`unpaidAmountFen`。  
`OrderItem`：`originalUnitPriceFen`、`actualUnitPriceFen`、`lineDiscountAmountFen`、`lineFinalAmountFen`。  
`Product`：`defaultPriceFen`、`defaultCostFen?`。  
`Payment`、`LedgerEntry`：`amountFen`。

金额规则：

```text
totalAmountFen = Σ(originalUnitPriceFen × quantity)
finalAmountFen = totalAmountFen - discountAmountFen
lineFinalAmountFen = actualUnitPriceFen × quantity - lineDiscountAmountFen
receivedAmountFen = downPaymentFen + 已确认收入回款 - 已确认退款
unpaidAmountFen = finalAmountFen - receivedAmountFen
```

订单项变更、订单金额重算、回款确认/作废/退款导致的应收重算必须由统一业务事务完成。

## 5. 状态、库存、账本与审计规则

### 5.1 状态拆分

Order 不再使用单一状态字段：

```text
businessStatus: DRAFT / CONFIRMED / COMPLETED / CANCELLED
paymentStatus: UNPAID / PARTIALLY_PAID / PAID / REFUNDED
```

OrderItem 分离采购和安装：

```text
purchaseStatus: PURCHASE_PENDING / PURCHASED / ARRIVED
installationStatus: WAIT_INSTALL / INSTALLING / DONE
```

状态映射：

| V20 OrderItem 状态 | 新采购状态 | 新安装状态 |
|---|---|---|
| NOT_ORDERED | PURCHASE_PENDING | WAIT_INSTALL |
| ORDERED / IN_TRANSIT | PURCHASED | WAIT_INSTALL |
| IN_STOCK | ARRIVED | WAIT_INSTALL |
| INSTALLING | ARRIVED | INSTALLING |
| INSTALLED | ARRIVED | DONE |

### 5.2 库存

V1 只使用 `InventoryItem + InventoryTransaction`。不实现预占、锁库、批次、库位或调拨。

每次入库、安装出库、手动调整、退货必须在同一 Room 事务中完成：

```text
读取余额 → 校验 → 更新 InventoryItem.availableQuantity → 写 InventoryTransaction

```

库存流水不可修改、不可删除；错误以反向流水修正。到货时入库，安装完成时出库；库存不得为负数。

### 5.3 回款与基础账本

Payment 不能物理删除。回款状态为 `ACTIVE`、`VOID`、`REFUND`；作废和退款保留完整历史。

LedgerEntry 是 V1 正式模块：

```text
收入：PAYMENT_INCOME、OTHER_INCOME
支出：PURCHASE_EXPENSE、OPERATING_EXPENSE、OTHER_EXPENSE
```

有效回款可以自动创建或关联唯一的 `PAYMENT_INCOME` 账本记录，防止账本收入重复统计。账本仅提供收入、支出、净收支统计；账本记录不可删除，只能作废。

### 5.4 ActionLog 覆盖范围

至少记录：登录安全事件、员工创建/禁用/启用、角色增加/移除、客户关键修改、订单关键修改、回款登记/确认/作废/退款、库存调整、备份与恢复。ActionLog 绝不因员工禁用或软删除而级联丢失。

### 5.5 密码安全

正式 V1 采用 `PBKDF2WithHmacSHA256`。每个员工使用独立随机 Salt、迭代次数、算法版本与派生哈希；验证使用恒定时间比较。禁止明文、MD5、单次 SHA-256。

## 6. AppConfig、Session 与备份恢复

### 6.1 唯一职责

| 存储 | 职责 |
|---|---|
| AppConfig（Room） | 门店配置、数据库版本诊断、最近备份/恢复信息 |
| SessionManager（DataStore） | 唯一运行时登录会话来源：staffId、storeId、登录状态 |
| PermissionManager（内存） | 当前会话的有效角色、权限与数据范围缓存 |

AppConfig 不保存当前登录员工，避免与 SessionManager 形成两套冲突来源。SessionManager 不保存权限真相。

### 6.2 备份恢复

V1 必须支持导出备份、备份元信息、校验、恢复前自动备份、关闭数据库后替换数据库文件、恢复后重新打开校验、清空登录会话、强制重新登录与恢复日志。

备份元信息至少包含数据库版本、备份时间、门店信息、各核心表数量和校验哈希。恢复后校验员工、客户、订单、订单项、回款、库存、账本、跟进、日志数量。

## 7. V20 基线与 Migration Fixture

### 7.1 真实数据规则

真实 V20 业务数据不保留、不使用、不进入 Migration Test。仅保留 V20 schema、当前代码结构和必要的数据库结构基线。

### 7.2 虚构 Fixture

创建完全虚构、可重复生成的 V20 Fixture，覆盖：

- BOSS、STAFF、SHAREHOLDER、禁用员工；
- 客户、订单、订单项、产品、供应商、库存、回款、跟进、账本；
- 工单状态日志和 ActionLog；
- 正常与边界金额：0.00、0.01、0.005、99.99、123.456、12,800.00、大额金额、优惠、首付款、部分回款、退款、收入和支出。

交付物：

```text
v20_fixture.db
v20_fixture_expected.json
v20_fixture_manifest.json
```

### 7.3 历史角色和客户负责人

| V20 角色 | V1 默认角色 |
|---|---|
| BOSS | BOSS + SALES + FINANCE |
| STAFF | SALES |
| SHAREHOLDER | FINANCE |

SHAREHOLDER → FINANCE 仅是迁移默认值，不代表历史岗位事实，绝不自动授予 BOSS。

V20 没有可靠 customer owner 来源时：

```text
Customer.ownerStaffId = NULL
```

禁止通过订单创建人、跟进人、备注文本或猜测回填负责人；UI 显示“未分配负责人”，由老板后续人工分配。

### 7.4 历史金额

所有历史金额统一：

```text
oldDouble × 100 → roundToLong() → Long（人民币分）
```

迁移后必须重新计算订单项、订单、有效回款、未收金额与 LedgerEntry 收入/支出，并做一致性验证。

## 8. Room Migration 原则与测试

### 8.1 Migration 原则

- 必须使用显式 Room Migration，禁止 `fallbackToDestructiveMigration()`。
- 不机械规定固定版本号链；实施时按 Entity 依赖、安全性和可单独测试性划分版本。
- V20 Fixture 必须能连续升级至最终 V1 schema；每个 Migration 单独测试，完整路径也必须测试，不允许跳过中间版本。
- Legacy Cleanup 独立实施，仅在新模型、业务代码和全部测试完全接管后删除旧字段。

建议依赖顺序：权限/配置 → 审计/责任/状态 → 金额/账本 → 库存流水 → Legacy Cleanup。

### 8.2 必测验收

| 类别 | 必测内容 |
|---|---|
| 数量 | Staff、Customer、Order、OrderItem、Payment、Inventory、LedgerEntry、FollowUp、ActionLog 数量一致 |
| 关系 | Customer→Order、Order→Item/Payment/Assignment、Product→Inventory、Staff→StaffRole 正确 |
| 金额 | Double→Long、订单项、总额、优惠、最终、回款、未收、账本收入/支出正确 |
| 库存 | 期初余额创建 InventoryTransaction；流水汇总等于最终库存余额 |
| 权限 | 角色迁移、权限映射、多角色并集、OWN/STORE 规则正确 |
| 审计 | 员工禁用或软删除后 ActionLog 存在；Payment/InventoryTransaction 不可删除 |

## 9. 架构与业务服务

保留 Compose、MVVM、Hilt、Room、Repository；不为了形式主义大规模重构。跨表复杂规则逐步集中到：

## 附录 A：阶段 0 前冻结修订（唯一有效）

本附录仅补充已冻结的 StaffRole、Payment 与订单金额规则；除本附录明确内容外，不重新设计产品范围、Entity 或权限体系。

### A.1 StaffRole 唯一关系与复用规则

`StaffRole` 必须保持 `staffId + roleId` 唯一。它表示员工当前角色分配状态，不承担完整角色历史版本记录。

- 移除角色时，更新原记录为 `isActive = false`、`removedAt = 当前时间`。
- 重新授予相同角色时，不插入新记录；更新原记录为 `isActive = true`、`removedAt = NULL`、`assignedAt = 当前时间`、`assignedByStaffId = 当前操作者`。
- 完整的角色增加、移除与重新授予历史仅由 `ActionLog` 保存。

### A.2 首付款与 Payment 的唯一真相来源

`Payment` 是全部实际收款和退款的唯一财务真相来源。订单创建时若实际收到首付款，必须创建 `paymentType = DEPOSIT` 的 `Payment`；`Order` 不得以 `downPaymentFen` 与 `Payment` 双重累计已收金额。

原 `downPaymentFen` 的业务含义冻结调整为 `agreedDepositFen`：合同约定应付定金，不表示已实际收款。实际收款始终以 `Payment` 为准。

`receivedAmountFen = SUM(有效且已确认的 INCOME Payment) - SUM(有效且已确认的 REFUND Payment)`。

### A.3 订单金额唯一计算规则

订单金额仅按以下公式计算：

- `originalTotalFen = SUM(originalUnitPriceFen × quantity)`
- `lineFinalAmountFen = actualUnitPriceFen × quantity - lineDiscountAmountFen`
- `itemsFinalTotalFen = SUM(lineFinalAmountFen)`
- `finalAmountFen = itemsFinalTotalFen - orderLevelDiscountFen`
- `receivedAmountFen = 确认收入 Payment 总额 - 确认退款 Payment 总额`
- `unpaidAmountFen = finalAmountFen - receivedAmountFen`

所有重算只能经由统一的 `OrderAmountCalculator` 或 `OrderService`。UI 和 ViewModel 不得各自实现另一套金额公式。
